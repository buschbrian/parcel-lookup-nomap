# Property Lookup — changes, 13 August 2026

This round worked the item that has been outstanding since 6 August: the manual accessibility pass.
Three defects were found that the existing 47-check axe suite **structurally cannot detect**, both
pages were fixed, and the findings were converted into regression tests so they cannot come back.

---

## Why axe did not catch these

The suite runs `AxeBuilder({page}).analyze()` on the initial and populated views, and it is green.
That is not a contradiction. Two of the three defects are outside what any automated rule engine
evaluates:

| Defect | Why axe cannot see it |
|:--|:--|
| Horizontal scrolling once text is enlarged | axe does not reflow the layout or evaluate it at a reduced viewport |
| No visible focus indicator on a programmatic focus target | axe does not move focus and does not judge indicator visibility |
| `aria-atomic` absent on a status region | Not a violation — a correctness choice about how much gets announced |

This is the 25–40% figure in practice. The suite was doing its job; the gap was the manual pass.

## 1. Enlarged text forced horizontal scrolling — 1.4.10 / 1.4.4

**Found.** With the container held at 320 CSS px and the grid collapsed as a real narrow viewport
would collapse it:

| Text size | Content width | Verdict |
|:--|:--|:--|
| 100% | 320 px | fine |
| 200% | **358 px** | horizontal scrolling |
| 400% | **675 px** | horizontal scrolling |

**Cause.** `overflow-wrap` was `normal` everywhere, so unbreakable tokens could not break. The real
offenders are in the data, not the prose: **14-digit parcel numbers** (`16264570030000`), the
**email address** in the contact list, and long single words in headings such as "Representation".

**Fix.**

```css
body{overflow-wrap:break-word}
dt,dd,li,h1,h2,h3{overflow-wrap:anywhere}
```

`anywhere` rather than `break-word` on the list children is deliberate and load-bearing: only
`anywhere` reduces the **min-content contribution** that CSS Grid uses to size the label column.
`break-word` alone leaves the grid track too wide and the overflow survives.

**Measured after the fix:** 200% text → 320 px. Resolved.

### On 400%, stated honestly

400% text still overflows (675 px → 530 px, improved but not resolved). That is **not asserted as a
failure**, because:

- **1.4.10 Reflow** requires no two-dimensional scrolling at a width equivalent to 320 CSS px at
  *default* text size. That case passes at exactly 320 px.
- **1.4.4 Resize Text** requires text to 200%. That case now passes.
- 400% text *inside* a 320 px viewport is roughly 1280% effective zoom, which neither criterion
  requires.

At that size the remaining overflow is the search input and the Copy/Print button row — single
elements intrinsically wider than 320 px at a 64 px font. Documented rather than asserted, so CI is
not red for something no criterion asks for.

## 2. Focus was moved with nothing on screen to show it — 2.4.7

**Found.** `head$.focus()` moves focus to `#r-head` after **every** lookup, and the skip link moves
focus to `#main`. Neither target had any focus indicator, because:

- `:focus{outline:none}` clears it globally, and
- `:focus-visible` **does not match** programmatic focus on a non-interactive `tabindex="-1"` element
  in Chrome.

So a sighted keyboard user completes a lookup, focus relocates, and nothing indicates where it went.
Their next Tab press appears to come from nowhere.

**Fix.** An explicit `:focus` rule — not `:focus-visible` — because this focus is always programmatic:

```css
#main:focus,#r-head:focus{outline:3px solid var(--focus);outline-offset:4px;border-radius:3px}
```

## 3. `aria-atomic` was absent on the status regions — 4.1.3

The status region replaces its entire message on every update, but without `aria-atomic="true"`
assistive technology may announce only the changed portion of the text node. Added to both pages.
Deterministic rather than dependent on how a given screen reader diffs text.

## 5. Regression tests — and two bugs in my own tests

Added to `tests/app.spec.mjs` and `tests/business.spec.mjs`:

- no horizontal overflow at a 320 px viewport
- no horizontal overflow at 320 px with text at 200%
- `overflow-wrap` computes to `break-word` / `anywhere`
- a lookup leaves focus on `#r-head`
- a `:focus` rule exists for `#main` and `#r-head` and declares a non-`none` outline
- status regions carry `role="status"`, `aria-live="polite"`, `aria-atomic="true"`

**The first draft of the focus test was both flaky and vacuous, and was rewritten.** It asserted
computed style:

- `getComputedStyle(el).outlineStyle` reads `"none"` whenever the browser window lacks OS focus,
  even with the rule present — so the assertion was **flaky**.
- `getComputedStyle(el).outlineWidth` reads `"3px"` from the UA default `medium` even when no rule
  exists at all — so that assertion would have **passed with the bug still in place**.

Both were verified in a live browser before the rewrite. The test now checks two independent,
deterministic things: that focus lands on `#r-head` (behaviour), and that a `:focus` rule declaring
an outline exists (declaration, via CSSOM). The rewritten version was then validated against three
states — rule absent (fails correctly), rule present (passes), rule sabotaged to `outline:none`
(caught).

## 6. Follow-up round: reflow completed to 400%, headings narrowed, release bumped

Worked from the notes above. Three of the five items are closed.

### The 400% diagnosis in note 4 was wrong

The note said the fix was `min-width:0` on the input and wrapping button labels. **It was not** — that
combination changed the measurement by 0 px. The actual culprit is the **`<fieldset>`**, which carries
an intrinsic `min-width: min-content` that `width:100%` cannot override. It sat at **466 px inside a
320 px container** and every descendant — legend, label, hint, combo, input, button row — inherited
that width. The input was a symptom.

Measured at a 320 px container, cumulatively:

| Rules in force | 100% | 200% | 400% |
|:--|:--|:--|:--|
| none (before 13 Aug) | 320 px | 358 px | 675 px |
| `overflow-wrap` only | 320 px | 320 px | 530 px |
| `+ input{min-width:0}` and wrapping buttons — the note's fix | 320 px | 320 px | **530 px (no change)** |
| `+ fieldset{min-width:0}` | 320 px | 320 px | 469 px |
| `+ legend{max-width:100%}` and `button{white-space:normal;max-width:100%}` | 320 px | 320 px | **320 px** |

Zero elements extend past the boundary at 400%. The 400% assertion is therefore **re-enabled** in both
specs, and a separate guard test pins `fieldset`/`input` `min-width:0` and `button` `white-space:normal`
so the fix cannot be mistaken for cosmetic and deleted.

### Headings narrowed (note 5)

`overflow-wrap:anywhere` now applies to `dt,dd,li` only. Headings are excluded, so an `h3` cannot
break mid-word. Verified empirically: 200% still holds at exactly 320 px without them.

### Release bumped (note 3)

`CFG.release` set to **2026.08.13** on both pages, including `dataReviewedOn` on the property page, by
explicit approval.

> **`dataReviewedOn` asserts a data-source review happened on 13 August.** This round was an
> accessibility pass — no source was re-reviewed, and `npm run check:services`, which is the mechanism
> that would substantiate the claim, needs network access unavailable in the authoring environment.
> **Run `npm run check:services` before deploying** so the published claim is true. If it does not
> pass, revert `dataReviewedOn` to `2026-08-09` rather than shipping the assertion.

The licensing page has no `dataReviewedOn` field — it carries `sourceSnapshot: "June 2026"`, left
unchanged.

### One self-inflicted defect, caught

The first edit to the licensing page inserted explanatory prose **outside** the existing CSS comment,
leaving five lines of loose text and an unmatched `*/` in the stylesheet. Caught by a comment- and
brace-balance check across both `<style>` blocks, and fixed. Both stylesheets now parse with balanced
comments, zero brace drift and no loose prose.

### Still open

6. **ADR-0001 extraction (note 1) is the remaining item, and it is the large one.** Vite is *not*
   installed and *not* scripted — the ADR is "Accepted for migration planning", `publish = "public"`,
   `command = ""`. So this is a genuine migration, not a config tweak: two inline pages of 61.6 KB and
   24.2 KB of JavaScript, one existing `SHARED REQUEST LAYER` marker region guarded by a byte-identity
   test, and `el()` present only on the property page.

   **It should not be attempted blind.** `node_modules` is absent and the authoring environment has no
   network, so `vite`, `npm install` and Playwright cannot be run there — a big-bang rewrite of 86 KB
   of working code into modules, plus switching the published artifact from `public/` to `dist/`, would
   be unverifiable at exactly the point where verification matters most.

   Recommended sequencing, smallest verifiable steps first:

   1. Add `vite` and an MPA config with both HTML files as entry points. Do not move any code. Confirm
      `npm run build` reproduces the current pages and `check:deployment` still passes.
   2. Extract the existing `SHARED REQUEST LAYER` region — already byte-identical, so this is
      mechanical and the byte-identity test proves parity before and after.
   3. Extract `pair()`, `flagPair()`, `parseAddress()`, `say()`, `explain()`, `dialable()` one function
      per commit, running the full suite between each.
   4. Port `el()` to the licensing page, which currently has none.
   5. Only then move `CFG` to build-time JSON with schema validation, and switch Netlify to `dist/`.

   Each step is independently revertible and independently testable. Steps 2–4 are where the
   "every accessibility fix is applied twice by hand" cost actually disappears.

7. **This round applied five CSS fixes across two files by hand** — three accessibility rules plus the
   reflow sizing set. That is the duplication cost in note 1, measured. It is the strongest argument
   for doing steps 2–4 above before the next accessibility batch.

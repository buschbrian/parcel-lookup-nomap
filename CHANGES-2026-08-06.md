Verified against live services and the deployed site
(`parcel-lookup-millcreek.netlify.app`). Deployment confirmed working: 31,887 address points
reachable, CSP permitting the queries.

## 1. Forgiving address search (the reported problem)

**The problem.** The search matched `FullAdd` with a single prefix `LIKE`. The County stores
addresses as `AddNum + PrefixDir + StreetName + StreetType + SuffixDir`:

| Stored | Components |
|:--|:--|
| `3300 E SANTA ROSA AVE` | 3300 · E · SANTA ROSA · AVE · — |
| `2760 S 2100 E` | 2760 · S · 2100 · — · E |

Residents type the words out. Confirmed failures before the fix:

| Typed | Result before |
|:--|:--|
| `3300 E SANTA ROSA` | found |
| `3300 EAST SANTA ROSA` | **no match** |
| `3300 East Santa Rosa Ave` | **no match** |
| `3300 E SANTA ROSA AVENUE` | **no match** |
| `2760 South 2100 East` | **no match** |

**The fix.** Normalise, then search in tiers, taking the first tier that finds anything:

1. **exact** — normalised string against `FullAdd`
2. **num + street** — `AddNum` plus `StreetName`, ignoring direction and street type entirely
3. **street only** — when no house number was typed
4. **broad** — `%contains%` on the street name

Normalisation handles: spelled-out directions (`EAST`→`E`), spelled-out street types
(`AVENUE`→`AVE`), punctuation, case, a trailing `, Millcreek, UT 84109`, and unit tokens
(`APT 4`, `#3`, `STE 200`).

All previously-failing inputs now resolve **on tier 1**, so there is no extra round trip in the
common case:

| Typed | After |
|:--|:--|
| `3300 East Santa Rosa Avenue` | tier 1 → `3300 E SANTA ROSA AVE` |
| `3300 EAST SANTA ROSA` | tier 1 → `3300 E SANTA ROSA AVE` |
| `2760 South 2100 East` | tier 1 → `2760 S 2100 E` |
| `3945 South 700 West` | tier 1 → `3945 S 700 W` |
| `3300 E Santa Rosa Ave, Millcreek, UT 84109` | tier 1 → `3300 E SANTA ROSA AVE` |
| `santa rosa` | tier 3 → 10 addresses to choose from |

**When the search is broadened, the user is told.** The live region announces e.g. "No exact match,
so the search was broadened. 4 address matches." Silently returning something other than what
someone typed is its own accessibility problem.

**A bug found during testing.** `toks.shift()` was consuming the house number *before* the
normalised string was captured, so tier 1 was searching for `E SANTA ROSA AVE` with no number and
never matched. Tier 2 was quietly covering for it. Fixed — tier 1 now works, which is why the
table above shows tier 1 throughout.

### Extending it — two config tables, no logic changes

- `CFG.address.synonyms` — spelled-out word → stored abbreviation.
- `CFG.address.streetAliases` — local variants. `MILL CREEK` → `MILLCREEK`, because the data
  stores it as one word.

**Rule for `streetAliases`:** only map a variant that does **not** already exist as its own street
name. Both `MILLCREEK CANYON` and `MILLCREEK CYN` exist in the data, so aliasing one to the other
would hide real addresses. This was caught and reverted during this round.

## 2. Recorded plat PDFs now linked

Confirmed: `Subdivision_Dissovle_3/FeatureServer/7` has `hasAttachments = true`, 976 subdivision
polygons, and every one sampled (6 of 6) carries exactly one plat PDF —
e.g. `El Serrito 2.pdf`, 2.4 MB.

The app now lists the attachment with descriptive link text:

> Recorded plat — EL SERRITO 2 (PDF, 2415 KB)

Never "attachment", never a bare URL — both fail 2.4.4 Link Purpose.

**These plats are scanned survey drawings and cannot be made accessible.** The app says so plainly
and pairs the link with the staffed route:

> **What this means.** Recorded plats are scanned survey drawings. They are images, so a screen
> reader cannot read them and they cannot be made fully accessible. If you need the information on
> the plat — lot dimensions, easements, setbacks — call 801-214-2754 and staff will read it to you
> or describe it.

This is deliberate. Linking the PDF is useful; implying it is accessible would not be. The wording
is also the **alternative access** that a §35.164 undue burden determination has to cite, so this
text does double duty — see the program plan, §4 and §7.

## 3. Water provider derived from the centroid, single answer

`Water_Services_2021/FeatureServer/**3**` — "Culinary Water Service Areas 2026". Layer index 3,
not 0.

Every layer in this app already queried the **parcel centroid** via `hits(lon, lat)`; water was no
exception. What changed is that it now reports **one** provider from that centroid instead of listing
every polygon covering it.

**Why.** A single point can only fall inside two service-area polygons if those polygons *overlap* —
which is a topology defect in the source data, not two real providers. Listing both presents a data
error to a resident as a fact about their property. `multi: true` was built, tested, and then
removed; the reasoning is left as a comment at the water layer config so nobody re-adds it without
reading it.

Verified on a 50-parcel sample: **50 with exactly one provider, 0 overlaps, 0 with no coverage.**
So the defect does not currently manifest at centroids — but the disclaimer below covers it if it
ever does.

**Six retail providers serve Millcreek** (the service is clipped to the city):

| Salt Lake City Water System | (801) 483-6900 |
| Holliday Water Company | (801) 277-2893 |

## 4. Standing data-quality disclaimers

New `CFG.GROUP_NOTES` mechanism: a permanent caveat attached to a whole results group, shown every
time — not only when something looks unusual.

**Services** — utility boundaries are compiled from the Utah Division of Drinking Water, UGRC and
providers. States plainly that they are approximate, contain known gaps and overlaps, are not always
updated when a service area changes, and are derived here from a single point inside the parcel. Ends
with: your bill or meter is the authoritative record, confirm with the provider before relying on it
for design, construction, a transaction or a connection application.

**Natural hazards** — FEMA and Utah Geological Survey products are approximate at parcel scale and
centroid-derived, so a property may be partly within a hazard area even where this reports "No". And
explicitly: this is not a flood determination for lending or insurance.

Rendered with a new `.note` style — grey, quieter than the amber `.callout`. That separation is
deliberate: a permanent caveat rendered in warning colours trains people to ignore warning colours.
Contrast verified at 9.72:1 light and 10.50:1 dark.

**These should not be removed.** If you add a group carrying third-party data, add a note for it.

## 6. "Failing to reach the address service" — diagnosed

**The deployed site is running an older build.** Checked directly at
`parcel-lookup-millcreek.netlify.app`: no `findAddresses`, no `parseAddress`, no `GROUP_NOTES`, and
no `water` layer. **The current `index.html` has not been pushed.**

**The service is not unreachable.** From the deployed page, `query()` returns a live count of 31,887
address points, and typing `3300 East Santa Rosa Avenue` through the real UI produces
*"No addresses match"* — not a service error. A battery of awkward inputs (`100%`, `3300 E_SANTA`,
`3300-E`, apostrophes) produced **zero** thrown errors.

**So the message was almost certainly `file://`.** Opening `index.html` by double-clicking it makes
the browser block the cross-origin request to ArcGIS. `fetch()` rejects, and the old code caught
*any* exception and reported "Could not reach the address service" — which is misleading, because
the service is fine and the browser is the thing refusing.

### That message was my bug, and it is now fixed properly

The old handler collapsed four unrelated failures into one sentence. Errors are now **classified**:

| Kind | Cause | What the user is told |
|:--|:--|:--|
| `file` | Page opened over `file://` | Explains the page must be served over http(s), with the developer fix |
| `network` | Offline, DNS, CORS or CSP block | Check your connection, then the phone number |
| `busy` | HTTP 429 rate limiting | Wait a few seconds and retry |
| `server` | HTTP 5xx or malformed JSON | "A problem at our end, not yours" |
| `query` | ArcGIS rejected the SQL (HTTP 200 + error body) | The search could not be processed |

Also changed:

- **Transient failures retry once** after 700 ms (`network`, `busy`, `server`). Rapid typing against
  a public ArcGIS service can hit a momentary limit; a single retry absorbs it.
- **`render()` moved outside the `try`.** Previously a rendering bug would have been reported as a
  network failure — the exact trap that made this hard to diagnose.
- **Real diagnostics go to the console** with the error kind, message and the failing URL.
- **A `file://` warning fires at startup**, so the problem is stated immediately rather than after
  someone types an address and blames the service.

### What to do

Push the current `index.html`. Test over `http(s)`, never `file://`:

```bash
python3 -m http.server 8080     # then http://localhost:8080
```

The tiered search in the new build is also what fixes the original "residents can't find their
property" complaint, so the deploy carries both fixes.

## 8. Services card: fireworks removed, congruent rows, provider-named links

**Firework restriction area removed** (`Firework_Restrictions_2019` layer 5). It was seasonal, and
because it had no configured `fields` the fallback grabbed the first three attributes it found —
which is where the irrelevant **Salt Lake County Council contact** under Services was coming from.
Removing the layer removed both problems. The removal is left as a comment with the reason.

**Every remaining layer is now explicitly configured.** The unconfigured fallback is a footgun for
resident-facing content, and this was the proof.

**Rows are congruent.** Electrical was the only unconfigured layer, so it rendered through the
fallback branch, which prefixed rows with `↳` while every configured layer did not. Both branches
now emit the same shape — first row `<Layer label> — <Field label>`, later rows just
`<Field label>`. No arrows anywhere.

**Links are titled with the organisation, not the field.** New `nameField` (read from the data) and
`linkName` (fixed string) options:

| Layer | Link used to read | Now reads |
|:--|:--|:--|
| Electrical | "Provider website" | **Rocky Mountain Power** |
| Water | "Provider website" | **Salt Lake City Water System** |
| Sewer | — | **Mount Olympus Improvement District** |
| Waste | "Wasatch Front Waste & Recycling" | **Wasatch Front Waste & Recycling District** |

Descriptive labels were kept where they already described the destination better than a name would
— "General Plan", "General Plan document", "Zoning ordinance", "Council Member page".

### A defect this surfaced: broken `tel:` links

The waste district's phone is stored as **`385468632`** — nine digits. The old code linked anything
phone-shaped, so it produced `tel:+1385468632`, a link that cannot connect. For someone who cannot
see that the number looks short, a dead link is worse than plain text.

Phone rendering now validates before linking:

| Stored value | Result |
|:--|:--|
| `(801) 483-6900` | link, `tel:+18014836900` |
| `801-262-2904` | link, displayed `(801) 262-2904` |
| `8012622904` | link, displayed `(801) 262-2904` |
| `1-888-221-7070` | link, `tel:+18882217070` |
| **`385468632`** | **plain text, not linked** |
| `3932 South 500 East` | plain text |

Bare digit strings are now also formatted for readability.

**Data fix needed at source:** correct the `PhoneNumber` value on `TrashPickupDays`. Once it is a
valid 10-digit number the app will link it automatically. Any number appearing as plain text in the
app is flagging a data defect.

## 9. Every row is self-describing; Services trimmed

**The ambiguity was real and worth fixing properly.** The Services card contained four rows labelled
simply "Phone" — waste, sewer, water, electrical. On screen you could infer ownership from position.
With a screen reader you could not: rows are read one at a time, so "Phone: (801) 262-2904" arrived
with no indication of whose number it was. Ambiguity that depends on remembering row order is an
accessibility defect, not a cosmetic one.

**Fix:** every row now reads `<Layer label> — <Field label>`, not just the first.

Layer and field labels were shortened accordingly, since the layer label is now prepended to every
row:

| Before | After |
|:--|:--|
| Waste & recycling pickup / Phone | **Waste & recycling — Phone** |
| Sewer district / Phone | **Sewer — Phone** |
| Culinary (retail) water provider / Phone | **Culinary water — Phone** |
| Electrical provider / Phone | **Electrical — Phone** |
| City Council district / Council Member | **City Council — Member** |
| Base zoning district / Zone code | **Base zoning district — Code** |

**Data changes applied:**

- **Trash phone now reads `phonenumberfix`.** The old `PhoneNumber` field has been removed from the
  layer entirely. The new value is `385-468-6325` — valid, so it renders as a working `tel:` link
  formatted `(385) 468-6325`. The phone validation added in §8 was what made the old broken value
  visible.
- **Sewer office address removed** (`address`). Not useful for a lookup.
- **Wholesale water supplier removed** (`WHOLESALER`). Residents deal with the retail provider.

Resulting Services card, verified live for `3300 E Santa Rosa Ave`:

## Verification

- JavaScript syntax: valid.
- Structural accessibility checks: **21 / 21 pass** (landmarks, heading order, labelled controls,
  combobox ARIA, live region, named buttons and links, no bare-URL link text, focus visibility,
  target size, reduced motion, print stylesheet, standing-note styling, no positive `tabindex`,
  no canvas, no iframe).

  10.50:1 dark, against a 4.5:1 requirement.

- Water single-provider behaviour: 50-parcel sample, 0 overlaps, 0 gaps.

**Still outstanding:** the manual keyboard-only pass and the NVDA pass. Automated checks catch
roughly 25–40% of WCAG issues, so no public conformance claim should be made until those are done.

## Notes for the next round

1. **Layer indices are not 0.** Council districts **2**, water service **3**, fireworks **5**,
   subdivisions **7**. Always read `<service>/FeatureServer?f=json` before configuring.
2. **The CSP is doing its job.** A call to `arcgis.com/sharing/rest/search` was blocked during
   testing because `connect-src` allows only `services9.arcgis.com`. If a future layer lives on a
   different host, add that origin to `_headers` or every query fails silently in the console.
3. **Consider the UGRC address locator as a later fallback.** Millcreek's org already has
   `masquerade.ugrc.utah.gov` configured as a geocoder. It would handle misspellings and
   partial-word matching better than `LIKE` ever will. It was deliberately *not* used here because
   the current approach queries the City's own authoritative address points and returns an exact
   `ParcelID` with no spatial query and no extra CSP origin. Worth revisiting only if residents
   still report failures.

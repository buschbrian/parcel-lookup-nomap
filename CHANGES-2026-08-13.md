# Property Lookup — changes, 13 August 2026

This round worked the item that has been outstanding since 6 August: the manual accessibility pass.
Three defects were found that the existing 47-check axe suite **structurally cannot detect**, both
pages were fixed, and the findings were converted into regression tests so they cannot come back.

---

## Why axe did not catch these

The suite runs `AxeBuilder({page}).analyze()` on the initial and populated views, and it is green.
That is not a contradiction. Two of the three defects are outside what any automated rule engine
evaluates:

| Defect | Why axe cannot see it |
|:--|:--|
| Horizontal scrolling once text is enlarged | axe does not reflow the layout or evaluate it at a reduced viewport |
| No visible focus indicator on a programmatic focus target | axe does not move focus and does not judge indicator visibility |
| `aria-atomic` absent on a status region | Not a violation — a correctness choice about how much gets announced |

This is the 25–40% figure in practice. The suite was doing its job; the gap was the manual pass.

## 1. Enlarged text forced horizontal scrolling — 1.4.10 / 1.4.4

**Found.** With the container held at 320 CSS px and the grid collapsed as a real narrow viewport
would collapse it:

| Text size | Content width | Verdict |
|:--|:--|:--|
| 100% | 320 px | fine |
| 200% | **358 px** | horizontal scrolling |
| 400% | **675 px** | horizontal scrolling |

**Cause.** `overflow-wrap` was `normal` everywhere, so unbreakable tokens could not break. The real
offenders are in the data, not the prose: **14-digit parcel numbers** (`16264570030000`), the
**email address** in the contact list, and long single words in headings such as "Representation".

**Fix.**

```css
body{overflow-wrap:break-word}
dt,dd,li,h1,h2,h3{overflow-wrap:anywhere}
```

`anywhere` rather than `break-word` on the list children is deliberate and load-bearing: only
`anywhere` reduces the **min-content contribution** that CSS Grid uses to size the label column.
`break-word` alone leaves the grid track too wide and the overflow survives.

**Measured after the fix:** 200% text → 320 px. Resolved.

### On 400%, stated honestly

400% text still overflows (675 px → 530 px, improved but not resolved). That is **not asserted as a
failure**, because:

- **1.4.10 Reflow** requires no two-dimensional scrolling at a width equivalent to 320 CSS px at
  *default* text size. That case passes at exactly 320 px.
- **1.4.4 Resize Text** requires text to 200%. That case now passes.
- 400% text *inside* a 320 px viewport is roughly 1280% effective zoom, which neither criterion
  requires.

At that size the remaining overflow is the search input and the Copy/Print button row — single
elements intrinsically wider than 320 px at a 64 px font. Documented rather than asserted, so CI is
not red for something no criterion asks for.

## 2. Focus was moved with nothing on screen to show it — 2.4.7

**Found.** `head$.focus()` moves focus to `#r-head` after **every** lookup, and the skip link moves
focus to `#main`. Neither target had any focus indicator, because:

- `:focus{outline:none}` clears it globally, and
- `:focus-visible` **does not match** programmatic focus on a non-interactive `tabindex="-1"` element
  in Chrome.

So a sighted keyboard user completes a lookup, focus relocates, and nothing indicates where it went.
Their next Tab press appears to come from nowhere.

**Fix.** An explicit `:focus` rule — not `:focus-visible` — because this focus is always programmatic:

```css
#main:focus,#r-head:focus{outline:3px solid var(--focus);outline-offset:4px;border-radius:3px}
```

## 3. `aria-atomic` was absent on the status regions — 4.1.3

The status region replaces its entire message on every update, but without `aria-atomic="true"`
assistive technology may announce only the changed portion of the text node. Added to both pages.
Deterministic rather than dependent on how a given screen reader diffs text.

## 5. Regression tests — and two bugs in my own tests

Added to `tests/app.spec.mjs` and `tests/business.spec.mjs`:

- no horizontal overflow at a 320 px viewport
- no horizontal overflow at 320 px with text at 200%
- `overflow-wrap` computes to `break-word` / `anywhere`
- a lookup leaves focus on `#r-head`
- a `:focus` rule exists for `#main` and `#r-head` and declares a non-`none` outline
- status regions carry `role="status"`, `aria-live="polite"`, `aria-atomic="true"`

**The first draft of the focus test was both flaky and vacuous, and was rewritten.** It asserted
computed style:

- `getComputedStyle(el).outlineStyle` reads `"none"` whenever the browser window lacks OS focus,
  even with the rule present — so the assertion was **flaky**.
- `getComputedStyle(el).outlineWidth` reads `"3px"` from the UA default `medium` even when no rule
  exists at all — so that assertion would have **passed with the bug still in place**.

Both were verified in a live browser before the rewrite. The test now checks two independent,
deterministic things: that focus lands on `#r-head` (behaviour), and that a `:focus` rule declaring
an outline exists (declaration, via CSSOM). The rewritten version was then validated against three
states — rule absent (fails correctly), rule present (passes), rule sabotaged to `outline:none`
(caught).

## 6. Follow-up round: reflow completed to 400%, headings narrowed, release bumped

Worked from the notes above. Three of the five items are closed.

### The 400% diagnosis in note 4 was wrong

The note said the fix was `min-width:0` on the input and wrapping button labels. **It was not** — that
combination changed the measurement by 0 px. The actual culprit is the **`<fieldset>`**, which carries
an intrinsic `min-width: min-content` that `width:100%` cannot override. It sat at **466 px inside a
320 px container** and every descendant — legend, label, hint, combo, input, button row — inherited
that width. The input was a symptom.

Measured at a 320 px container, cumulatively:

| Rules in force | 100% | 200% | 400% |
|:--|:--|:--|:--|
| none (before 13 Aug) | 320 px | 358 px | 675 px |
| `overflow-wrap` only | 320 px | 320 px | 530 px |
| `+ input{min-width:0}` and wrapping buttons — the note's fix | 320 px | 320 px | **530 px (no change)** |
| `+ fieldset{min-width:0}` | 320 px | 320 px | 469 px |
| `+ legend{max-width:100%}` and `button{white-space:normal;max-width:100%}` | 320 px | 320 px | **320 px** |

Zero elements extend past the boundary at 400%. The 400% assertion is therefore **re-enabled** in both
specs, and a separate guard test pins `fieldset`/`input` `min-width:0` and `button` `white-space:normal`
so the fix cannot be mistaken for cosmetic and deleted.

> **Superseded — this section's 400% conclusion is wrong.** The measurements above were taken at a
> 320 px *container* via in-browser script, not a 320 px *viewport*. When the re-enabled assertion was
> finally run in a real browser it failed: 149 px of overflow on the property page, 183 px on
> licensing. The cause was a third element again — the header logo. See §7.

## 7. Verification round: the suite was finally run, and it was red

Everything above was authored without network access, so `npm test` had never run against it. It has
now run on Windows with `node_modules` installed. **Two failures**, both the 400% reflow assertion §6
re-enabled: **149 px** of horizontal overflow on the property page, **183 px** on licensing.

### Why §6 read as resolved when it was not

§6 measured a 320 px **container**, by setting a width on an element and reading `scrollWidth` from a
script. The specs measure a 320 px **viewport**. Those are not the same test: a container inherits the
page's real layout context, and the header sits outside it. Every number in §6's table is defensible
and the conclusion drawn from them was still wrong.

**The general lesson is the one §5 recorded about the focus test, one round earlier:** an assertion
evaluated by hand in a console is evidence about the console, not about the suite. §5 caught it because
the rewrite was validated against sabotage. §6 did not, and shipped a false claim into a changelog and
a release bump.

### The cause: the header logo, a third distinct element

After `overflow-wrap` (§1) and the `fieldset` (§6), the remaining overflow was `.brand-logo`. It is
sized in `rem`, so at a 64 px root it reached **288 px** — past the 320 px boundary before a single
character of text — and `flex:0 0 auto` forbids it shrinking, so `.brand-copy` was pushed to
`right: 400 px`. A decorative image sized in text units is the defect: it carries no information, so it
must not scale with text.

```css
.brand-lockup{...;flex-wrap:wrap}
.brand-logo{width:5.5rem;max-width:88px;...}          /* and 72px in the ≤26rem query */
```

Measured in a **real 320 px viewport at 400%**, document overflow:

| Rules in force | Property page |
|:--|:--|
| neither | 149 px |
| `flex-wrap` alone | **32 px — still fails** |
| px caps alone, no `flex-wrap` | **0 px — passes** |
| both | 0 px |

**So the caps carry the criterion and `flex-wrap` does not.** The first draft of this fix asserted both
as load-bearing; that was wrong and is corrected in the CSS comments and both spec comments, so a later
reader does not delete the caps believing wrapping covers it. `flex-wrap` is kept for layout quality —
without it the copy is squeezed into a narrow column beside the logo instead of reflowing below it.

### The guard test, and an inconclusive sabotage check

Guard tests were added to both specs pinning `flex-wrap` and the logo's rendered width at 400%.

**The first sabotage check on that guard was inconclusive and nearly accepted as proof.** Removing the
cap from the base rule left the `@media (max-width:26rem)` cap in force — and that one alone is
sufficient at 320 px — so the guard passed and looked vacuous. Removing *both* caps produces 288 px
from the guard and 32 px of overflow from the reflow test, which is what makes the assertion
discriminating. **Two rules set the same property at the tested breakpoint; sabotaging one proves
nothing.**

**Result: 62 browser/axe pass, 23 unit, 4 Python.**

### `check:services` — 51/51, so `dataReviewedOn` is honest

Run against live services. All 22 endpoints, both known-parcel lookups, all 21 spatial queries, the
FEMA/Millcreek congruence cross-checks, the historic-designation distinction, the STR parcel and
400-foot buffer, and public-web-map parity across 21 adopted layers.

**`dataReviewedOn: 2026-08-13` is therefore substantiated** and the §6 instruction to revert it to

### `check:deployment` cannot pass, for a reason predating this round

It fails at its first assertion, `assert.equal(deployed, html)`. The deployed HTML matches **no commit
in the repository** — including the one live at the time — and differs by exactly five bytes:

```
repo:  <a href="/business-licensing.html">…</a>
live:  <a href='/business-licensing'>…</a>
```

That is **Netlify's Pretty URLs asset post-processing**: it parses the deployed HTML, rewrites links
ending in `.html` to their extensionless form, and re-serialises that one attribute with single quotes.
Evidence: the repository has exactly one `.html` href and the live page has zero, live carries exactly
one more single-quoted attribute than `dist/`, and no other line of 1710 differs.

**So the check is structurally unable to pass while that setting is enabled, and never could have
been.** It has apparently never been run with network access, which is why nobody noticed. Not a
deployment defect and not a regression — but **the post-deploy gate named in README.md, USAGE.md,
CODE.md and the DATA-SOURCES acceptance record has never actually gated anything.**

The assertions it aborts before reaching were run by hand instead, and they pass:

- **Security headers** — CSP, Permissions-Policy, Referrer-Policy, HSTS (`max-age=31536000`,
  `includeSubDomains`, plus `preload`), `nosniff`, and `max-age=0, must-revalidate`, all present on
  both pages with every asserted directive.
- **Publish allowlist** — 17 repository paths probed, 7 more than the script's list, including
  `MIGRATION.md`, `vite.config.mjs`, `package-lock.json` and `scripts/app-config.mjs`. **None is
  served.** `/netlify.toml` returns Netlify's own 404 page rather than the app, because Netlify
  reserves that path; that is why its body differs from the app's, and no repository content leaks.
- Both routes and the logo resolve: `/business-licensing`, `/business-licensing.html`,
  `/assets/millcreek-logo.png`.

**Not fixed here** — the choice is a judgment call about a security-relevant gate, not a typo:

1. **Normalise before comparing** — apply the same rewrite to the expected HTML. Keeps byte-exactness
   for everything else, but encodes a hosting behaviour into the test. **Note there are two
   transformations, not one** — see below.
2. **Turn Pretty URLs off in Netlify** and keep the assertion strict. `netlify.toml` already routes
   `/business-licensing` explicitly, so the feature is redundant here.

Option 2 is preferable: the redirect already exists, and it restores an exact-bytes gate rather than
teaching the gate to expect mutation. Either way the `/netlify.toml` probe needs to accept a 404.

**Post-deploy confirmation, and a second rewrite form.** After the fixes in this section deployed, the
live property page is **byte-equal to `public/index.html`** once the rewrite is applied — which rules
out any deployment drift beyond post-processing. The licensing page then exposed a second form:

| Page | Repository | Live |
|:--|:--|:--|
| `index.html` | `href="/business-licensing.html"` | `href='/business-licensing'` |
| `business-licensing.html` | `href="/index.html"` | `href='/'` |

The second is not extension-stripping — it is `/index.html` collapsing to the directory root. **Anyone
implementing option 1 must handle both**, or the licensing page will keep failing after the property
page passes. It is one more special case that option 2 avoids entirely.

The reflow fix was also re-verified against the deployed site rather than only locally: **0 px of
horizontal overflow at 100%, 200% and 400%** on both pages, logo capped at 72 px, `flex-wrap` active.

# Property Lookup — changes, 10 September 2026

One defect, found in production, fixed in both pages: a parcel with a detailed boundary could not be
looked up at all. Every ArcGIS query left the browser as a GET with the parcel polygon in the query
string, and the hosted service refuses a URL longer than about 2,048 bytes.

---

## 1. Oversized queries were rejected, and the page called it "Temporarily unavailable"

**Found.** Parcel `16273550010000` (2070 E 3335 S). Its boundary encodes to a query URL of about
3,700 bytes. Against the live services on 10 September 2026:

| Layer | Full URL bytes | GET | Same parameters as POST |
|:--|--:|:--|:--|
| Historic districts | 3,690 | **404** | 200 |
| Wildland-Urban Interface | 3,735 | **404** | 200 |
| Sensitive Land Areas | 3,700 | **404** | 200 |
| Millcreek flood layer | 3,704 | **404** | 200 |
| Fault study area | 3,689 | **404** | 200 |
| Liquefaction potential | 3,694 | **404** | 200, 1 feature |
| Debris flow | 3,707 | **404** | 200 |
| Alluvial fans | 3,685 | **404** | 200 |
| FEMA NFHL (different host) | 3,660 | 200 | 200 |

Every layer configured with `geometryMode:"parcel"` failed on the city's own hosted services. FEMA's
service tolerates the long URL, which is why the failure looked partial rather than total.

**What the resident saw.** Each failed layer rendered `Temporarily unavailable — call 801-214-2754`.
That is honest, but it is also every hazard and designation row on the page at once, and there is no
way for a reader to tell it apart from a service outage. About **12 of every 1,000 Millcreek
parcels** are over the limit, and they were over it on every lookup, every day — not intermittently.

**Cause.** `rawQuery()` built a `URL`, put the parameters in its query string and always sent a GET.
The parcel polygon is the only parameter that can be thousands of bytes long. Nothing in the page
measured the result.

**Fix.** `transportFor(fullUrl, cfg)` in the shared request layer measures
`new TextEncoder().encode(fullUrl).length` against the new `CFG.request.maxUrlBytes` (1900) and
returns `"GET"` or `"POST"`. `rawQuery()` encodes the parameters, builds the complete GET URL and
asks: at or under the limit the request goes out exactly as before; over it, the identical parameters
are posted to the same endpoint as `application/x-www-form-urlencoded`. `fetchJson()` takes an
optional third argument merged into the fetch options; the timeout, the cancellation contract, the
concurrency slot and the error classification are the same for both transports.

Both pages are fixed by one edit, because the shared request layer is byte-identical between them and
a unit test keeps it that way. `business-licensing.html` had the same defect in its 400-foot buffer
query, which carries the same parcel boundary.

---

## 2. Three decisions inside that fix worth stating

**The threshold is on the complete URL** — origin, path and query together — because that is what the
server counts. A longer service path leaves less room for the geometry, so a rule that measured only
the parameters would let the two add up past the limit undetected. The layer paths in `CFG` differ by
75 bytes today, and a service can be renamed.

**It is measured in bytes, not characters.** A URL that fits in 1,900 characters can exceed 1,900
bytes on the wire.

**The geometry is not shortened — ever.** The smaller change was to round coordinates
(`geometryPrecision`) until the URL fit. It was rejected: coordinate precision is what decides
whether a parcel touches a flood zone or a 400-foot short-term-rental buffer, so trimming the
boundary to fit a URL would quietly change the answers this page publishes. There is no rounding,
simplification or generalisation anywhere in the request path.

`maxUrlBytes` is 1900 rather than 2048 to leave margin for the proxies in between. Lowering it is
always safe — it only moves more queries to POST. Raising it past about 2000 brings the 404 back.

Nothing about hosting changed. Same origin, and `application/x-www-form-urlencoded` is a
CORS-safelisted content type, so there is no preflight and the CSP in `public/_headers` and
`public/staticwebapp.config.json` is untouched.

## 3. The monitor now sends what the page sends

`scripts/check-services.mjs` queried the same layers with the same geometries — as GET. Left alone it
would have started failing parcels the fixed page loads perfectly well, and, in the other direction,
a contract that passes as GET proves nothing about the transport a resident actually gets.

`scripts/service-contract-core.mjs` now carries a **textually identical** copy of `transportFor`, and
the monitor's `json()` helper applies the same rule: past the limit it posts the parameters to the
same endpoint. A unit test compares the two copies character for character — the same discipline that
holds the shared request layer byte-identical across the two pages.

Two new contracts, both contract-class (never retried, never softened):

- **`long-geometry-parcel`** queries every `geometryMode:"parcel"` layer with parcel
  `16273550010000` and requires a real answer from each. An empty feature array is a real answer —
  it is the parcel not intersecting that layer — so what is required is that all nine answer, and
  that at least one returns a feature, which a 404 can never do.
- **`long-geometry-transport`** is the boundary case: it fails if that parcel's query stops exceeding
  `maxUrlBytes`, and it checks that the rule switches at exactly the configured byte. A test parcel
  that quietly became short enough to fit would leave the first contract passing while proving
  nothing.

`npm run check:services` on 10 September 2026: **53/53 contracts hold**, including both new ones
(`long-geometry-parcel`: 9 polygon layers answered, 2 features; `long-geometry-transport`: 3,690
bytes, over the 1,900-byte limit).

## 4. Tests

**Unit (`tests/unit.test.mjs`).** A second extractor, `sharedBlock()`, evaluates the byte-identical
region on stubbed platform globals and hands back `transportFor` for direct testing — the helper
cannot move into the `pureApp()` region, because both pages have to call it. It is tested at 1,899,
1,900 and 1,901 bytes against two service paths of different lengths, with a multibyte character
(1,899 characters, 1,900 bytes) to prove the count is in bytes, and with no limit configured to prove
the old behaviour is the fallback. Two further tests: both pages configure `maxUrlBytes`, and the
monitor's copy of `transportFor` is textually identical to the page's.

**Browser (`tests/app.spec.mjs`).** The ArcGIS fixture now records every request's method, URL and
body, **and answers 404 to any GET over 2,048 bytes**, the way the real service does — without that,
the fixture would answer requests the service refuses and the transport tests would pass on a broken
page. Fixtures either side of the boundary: 41 vertices (longest query 1,888 bytes — still GET), 46
vertices (shortest 2,015 bytes — POST, with `geometry=` in the body and not in the URL), and a
200-vertex parcel. All of them must render real answers rather than "Temporarily unavailable", and
no GET in any lookup may exceed the configured limit. The vertex counts are measurements against the
configured layer paths, and the byte assertions fail loudly if a path change stops them straddling
the boundary.

**Browser (`tests/business.spec.mjs`).** A licensing parcel whose buffer query reaches ~2,300 bytes
is posted and still answers Yes/No, plus its counterpart: a buffer query that genuinely fails still
renders Unknown, never a false "No".

`npm test`: 62 unit checks, the Python flood-rank suite and 74 browser tests, all passing.

---

## What did not change

- No framework, bundler runtime or shipped dependency. Both pages remain self-contained inline
  vanilla JavaScript.
- No response-header change: `public/_headers` and `public/staticwebapp.config.json` are untouched.
- No version bump. This is a defect fix inside the published 2026.08.13 release; the next release
  will carry it.

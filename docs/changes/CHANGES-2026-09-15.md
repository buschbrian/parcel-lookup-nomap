# Property Lookup — changes, 15 September 2026

The 10 September work reached `main` today. Most of what it contains is already
recorded in `CHANGES-2026-09-10.md`; this file covers what is new since, what was
changed back, and — in the last two sections — what the merge itself exposed,
which is the more useful half.

One section here reverses a decision that changelog states. That is deliberate,
and is recorded as a reversal rather than quietly overwritten.

---

## 1. The property's own record leads the report again (PR #42)

`CHANGES-2026-09-10.md` §8 recorded zoning as the first section, so "a resident
hears what governs the property before the property's own facts". Reversed on
15 September: a resident who looked up an address sees the record for that
address first, and what governs it second.

`CFG.firstGroup` keeps its meaning — it names the LAYERS group that follows
Property record. The A7 fallback that existed to stop Property record being lost
when Zoning rendered no card is gone with the reason for it: Property record is
no longer placed by the group branch, so it cannot be lost.

## 2. The page now says when the parcel data changed, not only when it was checked (PR #42)

**Found.** The Property record said only "checked 9 August 2026". That is when
Millcreek last looked at the source, not when the source last changed. Salt Lake
County's parcel layer was updated on **3 September 2026** — after that check — so
the page named the older fact and nothing named the newer one. A resident reading
"checked 9 August" had no way to tell whether the data itself was that old.

**Fix.** A second field, read from the layer's own `editingInfo.dataLastEditDate`
(`1788466131325` = 2026-09-03 20:08 UTC, 14:08 local, so the local date is the
same day either way):

- `CFG.parcel.sourceUpdatedOn` and `CFG.release.dataUpdatedOn`
- `attributionNote()` renders `, updated <date>` only when a source declares one,
  so every other layer reads byte-identically
- the collapse key includes it, so two sources checked the same day but changed
  on different days no longer merge into one line that hides a date
- the copy footer names it beside `data sources reviewed`

`reviewedOn` keeps its meaning and its value. Overwriting it would have traded a
stale claim for a false one: the 9 August check did happen. Property record and
Location are the two cards affected — they attribute to `CFG.parcel` rather than
to a `CFG.LAYERS` entry.

## 3. Four review fixes that had been written but never shipped (PR #40)

**Found.** Fixes written on 11 September — after PRs #30–#36 were opened — were
never part of any of them. They existed only in one local checkout. Merging the
stack alone would have published this release without them, and they are not
cosmetic: they touch `index.html` and `scripts/service-contract-core.mjs`.

- ask for an object id only where one is read (A2-R01)
- refuse an unreadable polygon, and page coverage results in a defined order
- encode the parcel id, and guard the map scale on deep links
- do not append an empty note box to Property record

**How they landed.** As content rather than as their original four commits. The
branch they were written on is a rebase of the stack, so each fix was written
against a later state than the PR it belonged to — the A2-R01 fix carries an
`L.coverage` clause that has nothing to attach to at #36's head, because A3 had
not landed there. The originals are preserved on `rescue/work-a5-2026-09-15`.

## 4. A privacy notice on both footers (PR #41)

## 7. What the merge exposed about the merge process

None of this changed the product. All of it would have gone unrecorded, and the
first two very nearly shipped a wrong release.

**Retargeting is not automatic here, and the review said it was.** The merge
readiness review recommended `gh pr merge --delete-branch` on the understanding
that GitHub retargets the next PR onto `main` when its base branch is deleted.
`deleteBranchOnMerge` is `false` on this repository and the merges were run
without that flag, so nothing retargeted itself; every child needed an explicit
`gh pr edit <n> --base main` first. A loop doing retarget-then-merge also tripped
once with "Cannot change the base branch of a closed pull request" immediately
after a parent merged, and re-running from the PR it stopped at simply worked.

**The stack was never verified against `main` until the end.** Retargeting does
not re-trigger CI. `gh pr checks --watch` therefore returned instantly on results
computed against each PR's *old* base, and PRs #33–#36 merged six seconds apart
on them. Branch protection was satisfied and the content was equivalent, because
each parent was already in `main` — but the first genuine verification of the
stack against `main` was #36's own merge run, after all seven were already in.

## 8. The Vite pin tripwire worked, and the obvious way to satisfy it is wrong

`tests/unit.test.mjs` hardcodes the Vite version so that a Dependabot bump has to
fail a test and make somebody compare the built output. It did exactly that, and
the comparison is where the interesting part is.

**Building the Dependabot branch is not the comparison.** That branch sat 19
commits behind `main` — it predated the whole A stack. Built directly, its output
is 54 kB smaller than `main`'s and missing resident-facing strings including
"Zoning is the law now.", which reads exactly like Vite dropping content. It is
the A stack's absence, not Vite's doing.

Held the source fixed at `main` and varied only the Vite version:

| File | 8.2.2 | 8.3.0 | |
|:--|--:|--:|:--|
| `index.html` | 136,061 | 136,061 | identical |
| `business-licensing.html` | 43,551 | 43,551 | identical |
| `_headers` | 2,417 | 2,417 | identical |
| `staticwebapp.config.json` | 1,435 | 1,435 | identical |
| `assets/millcreek-logo.png` | 9,501 | 9,501 | identical |

Compared with `cmp`, not by size. The served pages do not move, so the literal
moved to `8.3.0`. Whoever repeats this: rebase first, then compare, then bump.

## 9. Link text repeated its own row label, on every coverage layer (PR pending)

**Found.** While screenshotting a real report for a hub thumbnail, parcel `16294760240000`
(1250 E 3300 S). The Zoning card rendered:

```html
<dt>Future land use — General Plan</dt>
<dd><a href="https://millcreekgeneralplan.com/">Future land use — General Plan</a></dd>
```

A screen reader announces the term, then the link, and hears the same phrase twice. Neither
announcement says where the link goes, or that of the two General Plan rows one is a web page and the
other a PDF.

**How wide it was.** The first diagnosis was wrong — it looked like two General Plan fields missing
link wording. It was every URL row on every **coverage** layer. Four rows in one report:
`Base zoning district — Read the code section`, both `Future land use` rows, and
`City Council — Member page`. The Council row arrived by a different route: a non-coverage layer with
neither `nameField` nor `linkName`, where the fallback behaved as designed.

**Cause.** `pair(dt, dd, cls, linkText)` falls back to `dt` when given no `linkText`. That is
deliberate — it exists so a link is never a bare URL (2.4.4 Link Purpose). But `linkText` was computed
*after* the coverage branch had already returned, so the coverage renderer called
`pair(o.label+" — "+lab, v)` with no fourth argument at all. It could never supply link wording, for
any layer, ever, and the fallback did exactly what it promises.

The zoning layer hid this because its field label reads as an action — "Read the code section" — so
the duplicate still described the destination. Only labels that are nouns made it visible.

**Fix.** `linkText` hoisted above the coverage branch so both renderers share it, guarded on
`o.attrs` because a coverage layer reaching that point can have none. New optional `linkNames` gives
**per-field** wording, which one per-layer `linkName` cannot do for a layer exposing two URLs:
`GENPLAN_WEBSITE` → "Read the General Plan online", `GENPLAN_DOCUMENT` → "Open the General Plan
document (PDF)", `CodebookURL` → "Read this zoning district in the Millcreek code". Council takes
`nameField:"COUNCILMEMBER"` — the mechanism that already exists for this, and which makes utility
links read "Rocky Mountain Power".

Content types were checked before the wording was written: `millcreekgeneralplan.com` returns
`text/html`, the DocumentCenter URL returns `application/pdf`. The "(PDF)" is verified, not assumed.

**Verified against the built artifact**, not the source: a rendered report for `16294760240000` now
reports **0 rows** where link text equals its own `<dt>`, down from 4.

**A latent trap, documented rather than fixed.** Coverage rows render from each designation's own
`feature`, but `linkText` reads `o.attrs`. No coverage layer sets `nameField` today, so they cannot
disagree. If one ever does, the link would be named after a different designation than its row. The
comment at the hoist says so.

### A test was changed, and that needs saying

`tests/app.spec.mjs:801` asserted the codebook link's accessible name was `"Read the code section"` —
it encoded the defect as expected behaviour and passed for as long as the defect existed. It now
asserts the new wording **and** that a link's text is never a word-for-word copy of its own `<dt>` —
the assertion the old test was missing. Declared here because RELEASE.md requires a changed assertion
to be recorded, and a test edited only to get a green run has stopped being evidence.

### Three defects this work introduced, caught in review before commit

1. The comment describing `linkText` was left at the old definition site, describing nothing.
2. The `nameField` comment named a sitting council member as its example; comments outlive terms.
3. The coverage/`o.attrs` caveat was not written down until review asked what happens when a coverage
   layer sets `nameField`.

  the GIS layers, it is not the release date, and per
  [ADR-0004](../decisions/0004-the-data-review-date-stays-human.md) it is not
  something a release step may advance on its own. It is 33 days old at this
  release; the 90-day warning is not due.
- No layer's `sourceOwner` or `reviewedOn` changed.
- No change to the request layer, the search tiers, or the disclaimer wording.

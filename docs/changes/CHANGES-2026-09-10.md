# Property Lookup — changes, 10 September 2026

One defect, found in production, fixed in both pages: a parcel with a detailed boundary could not be
looked up at all. Every ArcGIS query left the browser as a GET with the parcel polygon in the query
string, and the hosted service refuses a URL longer than about 2,048 bytes.

---

## 1. Oversized queries were rejected, and the page called it "Temporarily unavailable"

**Found.** Parcel `16273550010000` (2070 E 3335 S). Its boundary encodes to a query URL of about
3,700 bytes. Against the live services on 10 September 2026:

| Layer | Full URL bytes | GET | Same parameters as POST |
|:--|--:|:--|:--|
| Historic districts | 3,690 | **404** | 200 |
| Wildland-Urban Interface | 3,735 | **404** | 200 |
| Sensitive Land Areas | 3,700 | **404** | 200 |
| Millcreek flood layer | 3,704 | **404** | 200 |
| Fault study area | 3,689 | **404** | 200 |
| Liquefaction potential | 3,694 | **404** | 200, 1 feature |
| Debris flow | 3,707 | **404** | 200 |
| Alluvial fans | 3,685 | **404** | 200 |
| FEMA NFHL (different host) | 3,660 | 200 | 200 |

Every layer configured with `geometryMode:"parcel"` failed on the city's own hosted services. FEMA's
service tolerates the long URL, which is why the failure looked partial rather than total.

**What the resident saw.** Each failed layer rendered `Temporarily unavailable — call 801-214-2754`.
That is honest, but it is also every hazard and designation row on the page at once, and there is no
way for a reader to tell it apart from a service outage. About **12 of every 1,000 Millcreek
parcels** are over the limit, and they were over it on every lookup, every day — not intermittently.

**Cause.** `rawQuery()` built a `URL`, put the parameters in its query string and always sent a GET.
The parcel polygon is the only parameter that can be thousands of bytes long. Nothing in the page
measured the result.

**Fix.** `transportFor(fullUrl, cfg)` in the shared request layer measures
`new TextEncoder().encode(fullUrl).length` against the new `CFG.request.maxUrlBytes` (1900) and
returns `"GET"` or `"POST"`. `rawQuery()` encodes the parameters, builds the complete GET URL and
asks: at or under the limit the request goes out exactly as before; over it, the identical parameters
are posted to the same endpoint as `application/x-www-form-urlencoded`. `fetchJson()` takes an
optional third argument merged into the fetch options; the timeout, the cancellation contract, the
concurrency slot and the error classification are the same for both transports.

Both pages are fixed by one edit, because the shared request layer is byte-identical between them and
a unit test keeps it that way. `business-licensing.html` had the same defect in its 400-foot buffer
query, which carries the same parcel boundary.

---

## 2. Three decisions inside that fix worth stating

**The threshold is on the complete URL** — origin, path and query together — because that is what the
server counts. A longer service path leaves less room for the geometry, so a rule that measured only
the parameters would let the two add up past the limit undetected. The layer paths in `CFG` differ by
75 bytes today, and a service can be renamed.

**It is measured in bytes, not characters.** A URL that fits in 1,900 characters can exceed 1,900
bytes on the wire.

**The geometry is not shortened — ever.** The smaller change was to round coordinates
(`geometryPrecision`) until the URL fit. It was rejected: coordinate precision is what decides
whether a parcel touches a flood zone or a 400-foot short-term-rental buffer, so trimming the
boundary to fit a URL would quietly change the answers this page publishes. There is no rounding,
simplification or generalisation anywhere in the request path.

`maxUrlBytes` is 1900 rather than 2048 to leave margin for the proxies in between. Lowering it is
always safe — it only moves more queries to POST. Raising it past about 2000 brings the 404 back.

Nothing about hosting changed. Same origin, and `application/x-www-form-urlencoded` is a
CORS-safelisted content type, so there is no preflight and the CSP in `public/_headers` and
`public/staticwebapp.config.json` is untouched.

## 3. The monitor now sends what the page sends

`scripts/check-services.mjs` queried the same layers with the same geometries — as GET. Left alone it
would have started failing parcels the fixed page loads perfectly well, and, in the other direction,
a contract that passes as GET proves nothing about the transport a resident actually gets.

`scripts/service-contract-core.mjs` now carries a **textually identical** copy of `transportFor`, and
the monitor's `json()` helper applies the same rule: past the limit it posts the parameters to the
same endpoint. A unit test compares the two copies character for character — the same discipline that
holds the shared request layer byte-identical across the two pages.

Two new contracts, both contract-class (never retried, never softened):

- **`long-geometry-parcel`** queries every `geometryMode:"parcel"` layer with parcel
  `16273550010000` and requires a real answer from each. An empty feature array is a real answer —
  it is the parcel not intersecting that layer — so what is required is that all nine answer, and
  that at least one returns a feature, which a 404 can never do.
- **`long-geometry-transport`** is the boundary case: it fails if that parcel's query stops exceeding
  `maxUrlBytes`, and it checks that the rule switches at exactly the configured byte. A test parcel
  that quietly became short enough to fit would leave the first contract passing while proving
  nothing.

`npm run check:services` on 10 September 2026: **53/53 contracts hold**, including both new ones
(`long-geometry-parcel`: 9 polygon layers answered, 2 features; `long-geometry-transport`: 3,690
bytes, over the 1,900-byte limit).

## 4. Tests

**Unit (`tests/unit.test.mjs`).** A second extractor, `sharedBlock()`, evaluates the byte-identical
region on stubbed platform globals and hands back `transportFor` for direct testing — the helper
cannot move into the `pureApp()` region, because both pages have to call it. It is tested at 1,899,
1,900 and 1,901 bytes against two service paths of different lengths, with a multibyte character
(1,899 characters, 1,900 bytes) to prove the count is in bytes, and with no limit configured to prove
the old behaviour is the fallback. Two further tests: both pages configure `maxUrlBytes`, and the
monitor's copy of `transportFor` is textually identical to the page's.

**Browser (`tests/app.spec.mjs`).** The ArcGIS fixture now records every request's method, URL and
body, **and answers 404 to any GET over 2,048 bytes**, the way the real service does — without that,
the fixture would answer requests the service refuses and the transport tests would pass on a broken
page. Fixtures either side of the boundary: 41 vertices (longest query 1,888 bytes — still GET), 46
vertices (shortest 2,015 bytes — POST, with `geometry=` in the body and not in the URL), and a
200-vertex parcel. All of them must render real answers rather than "Temporarily unavailable", and
no GET in any lookup may exceed the configured limit. The vertex counts are measurements against the
configured layer paths, and the byte assertions fail loudly if a path change stops them straddling
the boundary.

**Browser (`tests/business.spec.mjs`).** A licensing parcel whose buffer query reaches ~2,300 bytes
is posted and still answers Yes/No, plus its counterpart: a buffer query that genuinely fails still
renders Unknown, never a false "No".

`npm test`: 62 unit checks, the Python flood-rank suite and 74 browser tests, all passing.

## 5. No query anywhere sends `outFields=*` (PR A2)

The transport fix above (§1–§3) shrank what the browser could not avoid sending — a parcel
boundary. It did not touch the other half of every one of those query strings: every layer query,
and the parcel record query in `load()`, asked ArcGIS for `outFields=*` — every attribute the
service happened to have, whether the page rendered it or not. Owner and mailing fields transited
on every layer query, not only the parcel query that actually shows them; `scripts/check-services.mjs`
had the identical pattern in its own four request producers.

**Fix.** A new pure helper, `outFieldsFor(L)`, returns the unique union of a layer's `fields`,
`nameField`, `rankField`, `oidField` (defaulting to `"OBJECTID"`) and `extraFields`; `hits()` sends
that instead of `"*"`. `parcelOutFields()` does the equivalent for the parcel record — `CFG.parcel`'s
named fields plus every `PARCEL_FACTS` and `PARCEL_FLAGS` field — and `load()` sends that. The
attachments lookup in `hits()` now reads the matched feature's object id through
`attrs[L.oidField||"OBJECTID"]` rather than a hardcoded `attrs.OBJECTID`.

**The two non-default object ids.** Verified 10 September 2026 against each service's own
`?f=json` metadata (`objectIdField`): `ccoz` (`/Zone_TCOZ/FeatureServer/0`) is `OBJECTID_1`, and
`council` (`/Millcreek_City_Council_Dist_2022/FeatureServer/2`) is `OBJECTID_12`. Every other
configured layer, including the FEMA NFHL host, uses `OBJECTID`. Both are now declared as
`oidField` in `CFG.LAYERS`, and `npm run check:services` enforces that the declared field actually
exists in the live schema for every layer, not only these two.

**The monitor follows the same rule.** `scripts/service-contract-core.mjs` gained
`layerFieldList(layer)` and `parcelFieldList(CFG)` — the same formula, exported so
`scripts/check-services.mjs` can import it rather than reconstruct it. `check-services.mjs`'s specs
array, its known-parcel query, its general spatial-query loop, the hazard-congruence query, the
long-geometry checks and the informational-hazard queries all now build `outFields` from one of
these two functions instead of `"*"`. A self-contained page cannot import a module, so `index.html`
still carries its own inline `outFieldsFor`/`parcelOutFields` — a unit test
(`tests/unit.test.mjs`, "the page's explicit field lists agree with the live monitor's") compares
the page's output against `layerFieldList`/`parcelFieldList` field for field, the same discipline
already used for `transportFor`.

**A side effect on the A1 fixtures.** Because every polygon-queried layer's query string is now a
few dozen bytes longer (a real field list instead of a single `*`), the two Playwright fixtures
calibrated in §4 to straddle `CFG.request.maxUrlBytes` no longer do: 41 vertices, previously the
longest GET at 1,888 bytes, now encodes to 1,915 and would have posted. Recalibrated by
measurement against the current configuration: `VERTICES_JUST_UNDER` is now 40 (longest query
1,889 bytes, the `hist` layer, still GET) and `VERTICES_JUST_OVER` is now 44 (shortest query
1,967 bytes, the `alluvial_fan` layer, POST). The test file's own comment already says why this
kind of drift is expected rather than a bug: these are measurements against the configured layer
paths, and now also against their field lists, not round numbers.

**The unconfigured-layer fallback stays, and stays provably dead.** `CFG.JUNK` and the
first-three-attributes fallback renderer in `draw()` are unaffected — a layer added later without
`fields` still needs them. A new unit test (`tests/unit.test.mjs`, "the unconfigured-layer fallback
renderer is currently unreachable") asserts every currently configured non-boolean layer declares
`fields`, so the fallback renders for none of them today; the test would fail the day that stops
being true, rather than the fallback quietly going untested.

**What did not change.** No dependency, no header, no version bump. The byte-identical shared
request layer is untouched — this only changes what callers pass as `outFields`, not how a request
is built or sent. `business-licensing.html` was checked and already named explicit fields on every
query; nothing there needed to change.

**Tests.** `tests/app.spec.mjs`'s `mockArcGIS` fixture now reads each request's `outFields` (GET
query string or POST body) and returns only those attributes, always supplying the layer's own
object id field when it was requested — so a field the page renders without requesting it now fails
the page's own content assertions instead of passing silently. A new test, "every query names its
fields explicitly, and every layer query includes its object id field", asserts no `/query` request
anywhere carries `outFields=*`, that every layer query's `outFields` includes its `oidField`, and
checks the address suggestion and parcel record queries — exempt from the object id requirement,
since neither identifies a resident's result by ArcGIS object id — against their own known,
already-explicit field lists.

`npm test`: 65 unit checks, the Python flood-rank suite and 75 browser tests, all passing.
`npm run check:services`: 53/53 live contracts hold, including the `ccoz` and `council` schema
checks now enforcing their non-default `oidField`.

## 6. Zoning was read from one point, and a point is not a property (PR A3)

**Found.** Two parcels, two different wrong answers, both from the same cause.

Parcel `15353000130000` reported **"Not in this area"** for base zoning. Its stored point falls in a
gap in the zoning map. The parcel itself intersects an A-1 district perfectly well — verified against
the live service on 10 September 2026: point query 0 features, boundary query 1.

Parcel `16263780070000` reported a single district. The zoning map draws a C-2 boundary against it,
so the property touches two districts; the stored point can only ever fall in one of them. Live on 10
September 2026: the boundary intersects C-2 and R-1-8, probe points inside the parcel confirm R-1-8
only, and no district contains the whole parcel.

Base zoning, future land use and the City Center Overlay were all configured to query the parcel's
stored point. "Not in this area" was the wording for a layer that returned nothing — which for
zoning is not a fact about the property at all. It is a statement no municipal lookup should make:
every parcel in Millcreek has zoning.

**Fix.** The three layers became *coverage* layers. Each is now asked three questions per lookup,
with standard ArcGIS parameters, against the same services, with no new host:

| | Question | How |
|:--|:--|:--|
| Q1 | What does the parcel boundary touch at all? | parcel polygon, `esriSpatialRelIntersects` |
| Q2 | Which of those cover real area inside the parcel? | a multipoint of probe points, `esriSpatialRelIntersects` |
| Q3 | Does one of them contain the whole parcel? | parcel polygon, `esriSpatialRelWithin` |

Q3's direction is not documented in the REST reference, so it is pinned by a live contract rather
than assumed: a 4 m square inside parcel `16261060200000` comes back under `Within` and not under
`Contains`, so `Within` means "the geometry I sent is inside the feature you return".

**The probe rule.** The centres of a 5×5 grid over the parcel's bounding box, offered together with
the parcel's stored point, each rounded to six decimals **first** and then kept only if the rounded
point lies strictly inside an outer ring and outside every hole, by even–odd ray cast. A point on a
ring is rejected. At most 25 are sent, which keeps the probe query at about 1,100 encoded bytes —
never the request that has to be posted. The stored point gets no privilege whatsoever: an exterior,
in-hole or on-boundary stored point is dropped like any other failing probe. If nothing survives, the
layer queries the stored point and says out loud that only the centre was checked.

Rounding applies to probe points and to nothing else. The parcel boundary is still never rounded,
simplified or generalised anywhere on this page — see §2.

**Probes are evidence of presence, never proof of absence.** A district the grid stepped over still
appears in the answer, marked as a touch the check could not confirm. Nothing Q1 finds is ever
suppressed, and **no percentage, size or proportion is ever published**, because none is measured.
The words "most", "small" and "too small" appear in none of these sentences, and a unit test walks
every state to keep it that way.

**Designation identity, not feature identity.** Two adjacent polygons that both say R-1-8 are one
answer to a resident. Zoning and future land use group by a field value (`ZONE_`, `LandUse`); the
City Center Overlay has no such field, because membership is the whole answer, so every feature it
returns maps to one constant local key and no designation field is requested. Q2 and Q3 ask for the
object id and nothing else and join back to Q1 by it; grouping happens after the join.

**What the resident is told.** The evidence produces one state, and each state has one explicit
sentence. Evaluated in this order: `failed`; `pointOnly-none` / `-one` / `-many` / `-unusable`;
`none`; `conflict`; `whole`; `overlap`; `split`; `present`; `unknown`; `unconfirmedOnly`. For
example:

- one district contains the parcel — "All of this property is in the R-1-8 zoning district."
- one district is probe-confirmed and none contains the parcel — "This property is in the R-1-8
  zoning district."
- two are confirmed — "This property has more than one zoning district. Part of it is R-1-8. Part of
  it is C-2. Call Planning and Zoning at 801-214-2700 to find out which rules apply to your project."
- a candidate the probes could not confirm, in **any** state — "The zoning map also touches this
  property with C-2. We could not confirm how much of the property it covers."
- nothing found, on a layer that should cover every parcel — "No zoning polygon was found at this
  property. That is a gap in the map, not a statement that this property has no zoning. Call Planning
  and Zoning at 801-214-2700."

"Not in this area" is now unreachable for all three layers.

**Health is reported separately from evidence.** A failed probe query does not make a district Q3
says contains the parcel any less contained, so the state describes what was found and a separate
line reports what could not be checked: "We could not confirm which of these covers this property.",
"We could not check whether one district covers all of this property.", "We could not read all of the
map for this property. Some information may be missing. Call Planning and Zoning at 801-214-2700."
Every one of them renders beside a real answer, never in place of one.

**A response is only an answer if it carries a `features` array.** A 200 with no such array is a
failed query, not an empty result — that distinction is the whole difference between "we do not know"
and a false "No". `exceededTransferLimit` is followed with `resultOffset` under three bounds: at most
`CFG.coverage.maxPages` (3) requests per query, a page that repeats an earlier page's object ids
stops it immediately, and every page carries the lookup's abort signal so Clear or a new search ends
it. Whatever arrived is kept, and the query is reported incomplete.

**The City Center Overlay** stays a Yes/No/Unknown row, and gains a distinction it did not have: an
edge-only touch no probe confirms now reads **Unknown**, not Yes. A boundary clipping the corner of a
property is not the property being in the overlay, and a resident told "Yes" would be told to meet
standards that may not apply to them. A complete query that finds nothing is still a real "No".

**Request budget.** Six more queries per lookup. `maxConcurrent` stays 12 and the burst test still
asserts the peak never exceeds it.

**Live contracts** (`npm run check:services`), all contract-class — never retried, never softened:

| Contract | Parcel | What it pins |
|:--|:--|:--|
| `zoning-coverage-known-parcel` | `16261060200000` | one district, and `Within` returns it |
| `zoning-boundary-overlap` | `16263780070000` | two candidates, probes confirm one, none contains the parcel |
| `zoning-gap-parcel` | `15353000130000` | the stored point matches nothing, the boundary matches a district |
| `spatial-relation-direction` | `16261060200000` | `Within` returns the containing parcel; `Contains` does not |

The monitor builds its probe points with the page's own `pointInRings` and `probePoints`, carried in
`scripts/service-contract-core.mjs` and compared character for character against the page's copy by a
unit test — the same discipline as `transportFor` in §3.

**Tests that changed, and why.** `mockArcGIS` became `spatialRel`-aware: it reads `spatialRel` and
`geometryType` (from the query string or the POST body) and answers per query role, with defaults
derived from the existing flat fixtures — the probe query returns what the candidate query returns,
and the whole-parcel query returns the single candidate when there is exactly one — so the pre-existing
browser tests keep their meaning. Every fixture feature now carries a distinct object id under its
layer's configured id field, or the object-id joins would all succeed and every coverage assertion
would be vacuous. Two existing tests changed: "full-parcel layers still run when parcel centroid
coordinates are missing" **inverted** — zoning now answers perfectly well without a centroid, and
Culinary water is the layer that genuinely needs one, so it is the one that must report the gap — and
the missing-geometry test gained the centre-only sentence, because a coverage layer without a
boundary now falls back to a real point query instead of reporting itself unavailable.

**What did not change.** No dependency, no header, no version bump, and the byte-identical shared
request layer was not touched — coverage needs nothing inside it. `business-licensing.html` is
unchanged.

**Addendum: three review findings against the above (A3-R01/R02/R03).** An independent inspection
found the state model above still had gaps between the intent and the code.

- *A3-R01.* `groupByDesignation()` dropped any Q1 feature missing an object id, so a readable
  designation with no id vanished and — worse — a Q1 response full of unreadable matches (a bare
  `attributes:{}` for CCOZ) landed on `candidates.size===0` and read as `none`: a confirmed "No" for
  the overlay, or the zoning gap sentence, neither of which the evidence supports. Fixed: a readable
  designation with no object id is kept as an unconfirmable candidate instead of being dropped; a
  feature that could not be identified at all is now counted separately (`unidentified`); and
  `coverageState()` only resolves `none` for a Q1 that is complete **and** genuinely empty — a complete
  but unreadable Q1 now resolves `unknown`, exactly like an incomplete one.
- *A3-R02.* `Number(null)` and `Number('')` both equal `0`, so a missing stored latitude or longitude
  passed a naive `Number.isFinite` validity check and was queried as a real point. Fixed: a new
  `validCoordinate(value, min, max)` rejects `null`, blank and non-numeric values before conversion and
  checks the result is in range, and `coverageHits()` serialises only the validated number.
- *A3-R03.* A non-boolean coverage layer with no designation to show (`none`, `unknown`,
  `pointOnly-none`, `pointOnly-unusable`) contributed only an unlabelled sentence paragraph — since
  base zoning and future land use share the "Zoning" card, two such fallbacks were indistinguishable on
  screen and in the copied text. Fixed: `draw()` now emits one labelled row (`<dt>` "`<Layer label>` —
  Result") for those fallback states, so every outcome names the layer it describes.

New unit truth-table cases in `tests/unit.test.mjs` and new `mockArcGIS` scenarios in
`tests/app.spec.mjs` (a `noOidSynthesis` fixture flag lets a scenario supply a feature the mock does
not silently complete with a default object id) exercise all three directly. See CODE.md §6.

## 7. The zoning rows were named after the wrong field, and the code section was not linked (PR A4)

**Found.** Verified live 10 September 2026 against `Zone_Update_2025___Related_Master/FeatureServer/2`'s
own `?f=json` metadata. The page's "Ordinance" row rendered `Zone_Desc1` — a purpose sentence such as
"R-1 zoning is designated for low density, single-household development within Millcreek." — under a
label that describes neither the value nor an ordinance. The row above it, "Category", rendered
`ZONE_DESC`, an all-caps duplicate (e.g. `RESIDENTIAL`) of the service's own sentence-case `Category`
field. Neither `CodeRef` (a Millcreek Municipal Code section, e.g. `18.36`) nor `CodebookURL` (a
`municipalcodeonline.com` link to that section) was requested or shown, even though the same service
carries both and the public Planning web map's popup already shows the code section and a link built
from them.

**Fix.** `CFG.LAYERS`'s `zone` entry now reads:

```js
fields:{ZONE_:"Code", Category:"Category",
        Zone_Desc1:"What this district is for",
        CodeRef:"Code section", CodebookURL:"Read the code section"}
```

`ZONE_DESC` is dropped in favour of `Category`, which says the same thing in sentence case.
`Zone_Desc1` keeps its row but gets a label that describes what it actually holds. `CodeRef` and
`CodebookURL` are new rows. No `nameField` is set on `zone` — coverage rows never pass a `linkText`
to `pair()` (see §6's rendering path in `draw()`), so a URL-valued row's link text falls back to
`pair()`'s own default, the row's `dt` (e.g. "Base zoning district — Read the code section"), never
the bare URL. `pair()` and `linkText()` needed no code change for this: the fallback that keeps a
link's text off a raw URL already existed for every other coverage row.

**Not added.** `ZoneName` is not shown. Verified 10 September 2026: it disagrees with `ZONE_` on the
same feature (`ZoneName` says `C` where `ZONE_` says `C-2`), and surfacing two names for one district
that can read differently would be worse than surfacing one. The discrepancy is recorded in
`DATA-SOURCES.md`'s zoning row for Planning to resolve; nothing on the page reads `ZoneName`.
`Res_Max_De` (a residential density figure) stays unrequested and unshown, per the existing "does not
display density" rule a unit test already enforced before this PR.

**Future land use has nothing to add.** `FutureLandUse_2024_Millcreek/FeatureServer/0` carries only
`LandUse`, `GENPLAN_WEBSITE` and `GENPLAN_DOCUMENT` — no analogous code-section or category split
exists on that service, so `futureland`'s `fields` are unchanged.

**Coverage grouping is unaffected.** Zoning groups candidate features by `designationKey:"ZONE_"` and
renders one row set per group (`draw()`'s coverage path: `o.shownKeys.forEach(key=>{ const
feature=(o.byKey.get(key)||[])[0]||{}; ... })`). The new fields are read from that same representative
feature, so each field still renders exactly once per designation, not once per underlying polygon —
no change was needed in the coverage logic itself.

**Tests.** `tests/unit.test.mjs` gained "zoning rows are named after what they hold and link the code
section": `zone.fields` carries `CodeRef` and `CodebookURL`, still lacks `Res_Max_De` and `ZONE_DESC`,
`zone.nameField` is unset, and the word "Ordinance" appears nowhere in `index.html`.
`tests/app.spec.mjs`'s zoning fixtures (`R18`, `R18_ADJACENT`, `C2`, and the default
`Zone_Update_2025___Related_Master` fixture) now carry `Category`, a `Zone_Desc1` purpose sentence,
`CodeRef` and a `CodebookURL`. A new test, "the code section and codebook link render alongside the
purpose sentence", asserts the "Code section" row renders `18.36`, the "Read the code section" row is
a link whose visible text is not a URL and whose `href` equals the fixture's `CodebookURL`, and the
"What this district is for" row renders the purpose sentence. The existing "two adjacent features with
the same code are one designation" test located its "Code" row by `hasText`, which is a substring
match; the new "Code section" row's text otherwise also matches that search, so the locator was
tightened to an exact match (`/^Base zoning district — Code$/`) rather than changing what it proves.

**Live check.** `npm run check:services` confirms the `zone` layer's declared fields exist in the live
schema — 10 September 2026: `ok zone /Zone_Update_2025___Related_Master/FeatureServer/2 20 fields`.

**What did not change.** No dependency, no header, no version bump, and the byte-identical shared
request layer was not touched. `business-licensing.html` is unchanged.

## 8. Zoning is now the first section, and each of zoning and future land use explains itself in one sentence (PR A7)

**Found.** Property record used to lead the report, with Zoning three headings later, once for the
overlay and once for a resident's own address, parcel number and owners. Zoning and future land use
are policy terms residents are not assumed to know; nothing on the page said, in one plain sentence,
what either one *is* before showing the value.

**Fix.** `CFG.firstGroup:"Zoning"` names the `CFG.LAYERS` group `draw()` places ahead of Property
record. `draw()` no longer appends the Property record card immediately after building it; it builds
every group's card through a `renderGroupCard(g)` function first, renders `CFG.firstGroup`'s card,
appends it, then appends Property record right after it — before the rest of the groups render in
their configured order. If `CFG.firstGroup` renders no card at all (every layer in it hidden, or the
group's own rows empty), Property record is appended first instead, so it is never dropped from the
page. The result:

```
Zoning → Property record → Historic designation → Hazard and special designations →
Subdivision and plat → Natural hazards → Informational hazard screening →
Representation → Services → Location
```

The results heading and the focus-to-heading behaviour are unchanged — `draw()` still sets
`head$.textContent` once at the top and calls `head$.focus()` once at the end, regardless of card
order.

Two `zone`/`futureland` `CFG.LAYERS` entries gained a new per-layer key, **`plainMeaning`** (a string,
not the existing `explain(e, what)` error-message function at line ~1028 — a different name was
picked on purpose to avoid the collision):

```js
// zone
plainMeaning:"Zoning is the law now. It sets what you may build on this "+
  "property and how you may use it today."
// futureland
plainMeaning:"Future land use is the city's plan for later. It is policy "+
  "in the General Plan. It does not change what you may build today."
```

## 9. A report can be opened by link and shared by link, and the map link lands on the property (PR A6)

**Found.** Nothing pointed at a specific property. Planning's public web map at
`https://planning.gis.millcreekut.gov/` already accepts `?lon=&lat=&scale=` (WGS-84, six decimals;
a malformed pair is ignored and the map opens at its default view), and that map's own Property
information popup is being wired to send `?parcel=<14 digits>` or `?address=<text>` to this page —
but this page did not read either one, and its own "interactive zoning map" link only ever opened
the map's default city-wide view, never zoomed to the property being reported on.

**Fix.** Three additions, all outside the byte-identical shared request layer.

**Two query readers.** `parcelFromQuery(search)` accepts `?parcel=` matching `^\d{9,14}$` and pads
it to 14 digits with the same rule the submit handler already uses; `addressFromQuery(search)`
accepts `?address=` trimmed to no more than 120 characters. Both return `null` for anything else —
missing, malformed, wrong length, a stray `<script>` — rather than guessing or throwing, so the page
opens exactly as it does with no query string at all. Neither reads `URLSearchParams`: both live in
the pure region a unit test evaluates inside a bare `vm` sandbox with no browser globals, so the
query string is parsed by hand instead.

**Boot reads the query string once, right after `$("#build")`.** A valid parcel id calls
`load(id, id)` directly — a report with no typing at all. A valid address fills `#q` and calls
`requestSubmit()` on the existing form, so it runs through the identical tiered search a resident's
own typing would run, several-candidates branch included, rather than a second search path that
could quietly disagree with the first.

**A successful lookup makes its own URL shareable, and only the parcel id is ever written.**
`load()` calls `history.replaceState(null,"",location.pathname+"?parcel="+parcelId)` immediately
after a successful `draw()` — never on a failed lookup, and never with the typed address. SECURITY.md
is why: the page holds no accounts and no resident-submitted data, and a typed address plus a shared
link is not itself public record the way the parcel id is, so nothing about what a visitor typed is
ever written to a URL a browser keeps in history. `pushState` is never used — there is no `popstate`
handler, so a new history entry per lookup would only make the Back button appear to do nothing.
Clearing the form now also calls `history.replaceState(null,"",location.pathname)`, dropping
whichever parameter the page opened with: a cleared report does not reload on refresh, and a cleared
address deep link does not re-run its search.

**The map link now lands on the property.** A new pure helper, `mapLinkUrl(base,{lon,lat,scale})`,
returns `base+"?lon="+lon.toFixed(6)+"&lat="+lat.toFixed(6)+"&scale="+scale` when `lon`/`lat` are
finite numbers, or the bare `base` otherwise — the same fallback the planning map itself uses for a
malformed pair. `draw()`'s Location card already has `lat`/`lon` in scope from the parcel record, so
the "interactive zoning map" link now reads `mapLinkUrl(CFG.fallbackMapUrl,{lon,lat,scale:
CFG.mapLinkScale})`. The new `CFG.mapLinkScale` is `2000`, derived from the planning map's own
address-result box, which zooms to roughly ±180 ft around a point — 1:2000 approximates that framing
rather than opening zoomed out to the neighborhood. Link text stays "interactive zoning map", and no
`tool` parameter is added by default.

**Not changed.** `CFG.fallbackMapUrl` and `CFG.referenceWebMap.appUrl` already pointed at
`https://planning.gis.millcreekut.gov/`; neither was touched. Nothing about the parcel record query,
coverage logic, or field lists (A2–A4) changed — this is new boot-time behaviour and one new render
path for one existing link, not a change to what a lookup asks for or shows.

**Tests.** `tests/unit.test.mjs` gained truth tables for all three helpers: `?parcel=abc`,
`?parcel=<script>`, 8 vs. 9 vs. 14 vs. 15 digits, an over-long address, a missing lon or lat, and
rounding to six decimals; plus a check that `CFG.mapLinkScale` is a positive number.
`tests/app.spec.mjs` gained: `goto("/?parcel=16264570030000")` renders results with no typing and
announces "Results ready" in `#status`; `goto("/?address=3300%20E%20Santa%20Rosa%20Ave")` runs the
same tiered search typing it would; a normal lookup leaves `page.url()` ending `?parcel=<id>`; a
failed lookup (a new `parcelNotFound` mock option) leaves the URL exactly as it was; lookup → Clear
→ reload shows an empty form; Clear on an address deep link removes the parameter; the map link's
`href` carries `lon`, `lat` and `scale`; and axe reports no violations on a deep-linked page.

**`tests/production.spec.mjs` was not changed.** Its shared `smoke()` helper already blanks
`#results-body` in a `finally` block before writing evidence, for any flow or path it is given —
that rule does not depend on which URL was loaded, so a `?parcel=` case would inherit it rather than
need it re-proven. It was left out anyway: every case in that file is a real request against live
production services and real resident data, run by hand rather than on every change, and the
deterministic `tests/app.spec.mjs` cases above already prove the deep-link behaviour itself. Adding
a live case is a reasonable future addition, not one this PR needed to make.

**What did not change.** No dependency, no header, no version bump, and the byte-identical shared
request layer was not touched — deep links need nothing inside it. `business-licensing.html` is
unchanged. No coverage, field or ordering change (A2–A4, A7).
